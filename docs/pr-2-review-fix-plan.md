# PR #2 レビュー指摘への修正計画

2026-10-21。対象は [PR #2](https://github.com/shousui-works/kotokoto-wellness/pull/2)、精査した先端は `1f9bd5a6aa01558cf89c808be78de2bf6a823ecf`。

コードと架空データによるローカル検証で分類した。以下の7件はこの計画に沿って実装・検証済み。結果は末尾に記載する。外部サービスへの再レビュー依頼、デプロイ、マージはこの計画の対象外。

## 今回の対応範囲

本番コード4件、認証経路の安全な既定値への変更1件、検証用コード2件を扱う。変更箇所を指摘の原因に絞り、無関係な整形・機能追加は行わない。まず失敗する回帰テストを追加し、最小限の修正、関連テスト、自分自身による差分の再レビューの順に進める。

### 1. ハンドラー例外をHTTP境界で処理する

- [指摘](https://github.com/shousui-works/kotokoto-wellness/pull/2#discussion_r4331430263)。隔離したNodeプロセスで、ハンドラーのrejectにより終了コード1となることを再現した。通常の入力だけで必ず発生するという意味ではないが、例外に対する防御が不足している。
- `server/index.mjs` のaccount/chatハンドラー呼び出しを境界で捕捉する。ヘッダー送信前は汎用500、送信済みなら接続を閉じる。会話、トークン、例外本文をログや応答へ出さない。
- 回帰テスト：同期throwと非同期rejectの双方、送信途中の例外、例外後も次の正常なリクエストを処理できること。未処理のrejectionがテストランナーを終了させないよう、必要な再現は子プロセスで隔離する。

### 2. 認証なしの旧チャットを本番起動時の既定値から外す

- [指摘](https://github.com/shousui-works/kotokoto-wellness/pull/2#discussion_r4331430286)。`legacy` ではCookieのみで旧チャットに到達することを固定応答で確認した。一方、`required` では未ログインが401となり、旧経路への認証迂回は再現しなかった。
- `createAppServer` の既定chatハンドラーを無効にし、明示的に注入された場合だけ扱う。本番はアカウントAPIでのみ実AIへ接続する。静的配信・legacyの端末内記録は維持し、ローカルプレビューと既存チャット単体テストは固定応答のハンドラーを明示的に渡す。
- GCP設定やTerraformの既定値はこの修正に混ぜない。認証設定が未準備の環境で実AIを使えなくする、という意図した挙動変更をPRの説明へ記載する。
- 回帰テスト：APIキー相当の値があっても通常起動の未認証要求からAIを呼べないこと、requiredの未ログインは401、認証済み会話は従来どおり、明示的なオフラインプレビューは利用可能であること。

### 3. 401で未確認の保存コマンドを消さない

- [指摘](https://github.com/shousui-works/kotokoto-wellness/pull/2#discussion_r4331430215)。401後にUID別のpendingが消えることを再現した。
- `dist/account-client.mjs` のmutateで、401のときはpendingと要求ID・編集時revisionを保持する。認証失効中に保存や同期を強行しない。同じUIDで再ログインした後、本人の再試行で元の操作を確認する。別アカウントへの切替・明示的なログアウトの分離は維持する。
- 回帰テスト：401後のlocalStorage保持、同じUIDでクライアントを再作成して同じ要求IDで再試行、重複保存なし、別UIDには引き継がないこと。401以外の確定した4xxの既存処理も確認する。

### 4. 取り込み内容と要求IDの不一致から復帰できるようにする

- [指摘](https://github.com/shousui-works/kotokoto-wellness/pull/2#discussion_r4331430242)。取り込み失敗後に名前を変えると、同じIDのまま409が続くことを再現した。
- `request_conflict` が確定した場合に限り、保存した取り込みIDを解除し、本人の次の再試行で新しいIDを発行する。通信結果が不明な失敗や処理中の応答ではIDを捨てず、自動的に別要求として送らない。元のローカル記録は消さない。
- 回帰テスト：ステージング失敗→名前変更→409→次の操作で新しいID、同じ内容の通信再試行では元のID、すでに有効なクラウドデータは置換しないこと。既存の中断ステージング清掃の実装は追加しない。

### 5. 日付補正を該当する行動の文脈に限定する

- [指摘](https://github.com/shousui-works/kotokoto-wellness/pull/2#discussion_r4331430273)。「昨日は疲れて休んだけど、今日は20分歩いた」が前日扱い、「いつも覚えてるよ。20分歩いた」が日付不明になることを再現した。
- `server/komugi-chat.mjs` ではまず当該evidence内の明確な日付表現を確認する。発言全体を参照する補助処理は、該当行動との対応が一意な短い発言に限り、別の文・別行動の「昨日」や「いつ」を適用しない。曖昧な場合はLunaの候補日を不用意に上書きしない。
- 提案パッチをそのまま適用しても「いつも覚えてるよ」の誤判定が残るため、日付不明の表現も実施日の不明を示す文脈に限定する。
- 回帰テスト：上記2例、昨日/一昨日の単独報告、今日と昨日が混ざる報告、複数行動、実際に日付を覚えていない報告、既存行動の日付訂正。未来日の拒否と重複防止も維持する。

### 6. 検証用固定応答で予定・未実施を達成扱いしない

- [指摘](https://github.com/shousui-works/kotokoto-wellness/pull/2#discussion_r4331430295)。`test/preview-report.mjs` の「ストレッチしたい」「まだ歩いたことがない」が候補として通ることを再現した。本番Lunaの誤判定を直接示すものではない。
- 固定応答が対応する発言パターンを実施済みのものへ絞る。否定・希望を検証したい場合はactionsを空にし、架空の実施を褒めない。固定応答を本番並みの自然言語パーサーへ拡張しない。
- 回帰テスト：実施済み、希望、予定、否定の各例と歩行の判定。固定応答関数の検証で待受サーバーが勝手に起動しないよう、最小限の分離または起動条件を設ける。

### 7. 検証用の間食候補に実在するevidenceを使う

- [指摘](https://github.com/shousui-works/kotokoto-wellness/pull/2#discussion_r4331430303)。「お菓子を控えられた」で、固定の引用文が入力にないためinvalid_replyになることを再現した。これも検証用コードだけの問題。
- 固定応答のsnack候補は、対応した入力に実際に含まれる部分をevidenceとする。
- 回帰テスト：短い間食報告と従来の長い固定例の双方がextractReportを通り、予定・否定は候補にならないこと。6と同じテストで検証して重複を避ける。

## 今回修正しない指摘

### 45秒タイムアウト：現行の認証あり経路では誤検知

[指摘](https://github.com/shousui-works/kotokoto-wellness/pull/2#discussion_r4331430250)。`komugi-conversation.mjs` に45秒の記述はあるが、appから渡す `account.fetch` 内で、実際のfetchへ渡すsignalを55秒で作り直す。呼び出し元のsignalは合成されていない。注入したfetchで55,000msのsignalが使われ、呼び出し元の中断signalが伝わらないことを確認した。本番の返事生成は `createReportGenerator({timeoutMs:25000})`、要約は20秒である。

日次要約をしない旧経路では45秒の待機に対して返事生成は30秒。この指摘の「日次要約のある認証あり会話が45秒で中断される」という説明は現行経路には当たらない。二重に見えるタイムアウト指定の整理は可能だが、不具合修正とは分ける。根拠を返信し、この指摘はResolveする。

### Firestoreの全件再取得：別PRの改善課題

[レビュー内の改善提案](https://github.com/shousui-works/kotokoto-wellness/pull/2#pullrequestreview-5593095617)。各atomicがloadを呼び、日別記録・行動・直近会話を再取得するという指摘は正しい。ただし初期実装の全件読取と後続のページ分割は既存設計に明記されている。変更のない定期同期はreadIfChangedで親文書だけを確認しており、すべての同期が全件取得になるわけではない。

別PRではまず `/api/operations/:id` を操作文書と必要なメタ情報だけで処理する経路に分ける。その後に会話/コマンドごとの読取範囲と集計の保存方式を設計する。現在のポイント計算、訂正、体重参照、記憶、トランザクションの整合性を壊さないため、全件読取の一括置換は今回行わない。比較用の読み込み文書数を測定するテストも追加する。

この提案はレビュー本文内のnitpickで、独立したResolve可能なスレッドはない。レビューへの補足コメントで今回見送る理由と本計画を案内する。

## 実装・検証結果（2026-10-21）

- 7件を実装した。ハンドラー例外は汎用500または接続終了として扱い、通常起動から旧チャットへの既定のフォールバックを削除した。認証未準備のlegacy環境でも、実AIを利用できない挙動へ変更している。明示的な固定応答プレビューは維持する。
